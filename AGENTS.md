# AGENTS.md — working rules for this repo

This file is the contract for any agent or contributor changing **GigaPrompt Tower Defense (GPTD)**. Read it before editing. Its purpose is to keep the code, the docs, and the player-facing copy from ever drifting out of sync.

---

## 0. The golden rule — nothing goes stale

**Any change to behaviour, content, mechanics, balance, or UI text MUST be propagated to every document and locale it touches, in the same change.** A PR that updates the game but leaves the manual or design doc describing the old behaviour is incomplete.

When you change code, ask: *who describes this?* Then update all of them:

| If you change… | Also update… |
| --- | --- |
| A mechanic / serving rule / failure mode (any of the seven outcomes) | `docs/BLUEPRINT.md` is the authoritative design spec and `docs/REFERENCE-DOSSIER.md` the real-world grounding — **cite them, do not contradict them**; `docs/DESIGN.md` (the canonical GDD — keep it current), `docs/REALISM.md` (basis + known deviations), `docs/manual/*.md`, in-game tutorial / Codex / tooltips if affected |
| A formula or constant in `src/sim/**` or `src/config.ts` | `docs/MATH.md` |
| A roster model (add / edit / correct) | **`docs/MODEL-CATALOG.md`** first (the fact-checked source of truth), then the model data + regeneration (§3 *Add a model*); `docs/PARETO.md` and the catalog's generated lines come from `scripts/roster-report.mjs`; tests that name a model id; i18n only if the display name is localized |
| A request archetype / hardware / infra node / post-training recipe / guardrail / wave / incident (stats, cost, behaviour) | `docs/manual/*.md` tables, and the **i18n strings** for its name/description (§4); confirm `docs/BLUEPRINT.md` still describes it correctly |
| The wave campaign (count, order, names, difficulty curve) | `docs/manual/*.md`, the in-game menu/HUD copy, the zh-TW `wave.<i>.*` strings |
| How an outcome or event looks or sounds | `src/outcomes.ts` (`OUTCOME_STYLE`), the manuals' board legend and sound cues; run `pnpm audio:check` when a cue or the mix changes |
| Any **player-facing string** | **both** `src/i18n/en.ts` and `src/i18n/zh-TW.ts` (never hardcode — see §4), and the manuals if they quote it |
| Controls / keybindings | `src/ui/help.ts` (the one hotkey table), `docs/manual/*.md` controls table, the in-game tutorial (Codex) |
| Settings / system menu | `docs/SYSTEM-MENU.md`, the manuals' settings section |
| Agent actions, the `/state` snapshot, rejection reasons | `docs/AGENT-BRIDGE.md`, the `HELP` block in `public/bridge.mjs` |
| Tech stack / scripts / structure | `README.md`, and §1 / §2 here |

Docs in this repo and who they serve. **All documentation lives in `docs/`** (the player manual in `docs/manual/`); `README.md` and this `AGENTS.md` stay at the repo root. See `docs/README.md` for the index.

- **`docs/BLUEPRINT.md`** — the **authoritative design spec** (§0–§7: the unified data model, the serving spine, dual-clock/SLO physics, every subsystem). This is the single source of truth for current mechanics — **cite it, never contradict it**. The CODE is the ultimate truth; verify specifics against `src/sim/**` and `src/core/types.ts`.
- **`docs/REFERENCE-DOSSIER.md`** — the **real-world grounding** (real GPU specs, model figures, public benchmarks, serving-systems literature) the sim is calibrated against. The blueprint's `§ref` citations resolve here.
- **`docs/DESIGN.md`** — the **canonical Game Design Document** (the readable design of record). The blueprint is the deeper implementation spec; keep DESIGN.md current whenever a shipped behaviour shifts.
- **`docs/MATH.md`** — the math reference (every formula/constant/variable, extracted from the code).
- **`docs/REALISM.md`** / **`docs/REALISM-MODELS.md`** — the realism ledgers (mechanic → real-world basis, citations, known deviations; the model roster and its calibration pipeline), reconciled to the current code. The sim is meant to be defensible in front of LLM-infra professionals (*"the board is the metaphor, the numbers are real"*) — challenge every new technique against its real-world tradeoff directions.
- **`docs/MODEL-CATALOG.md`** — the fact-checked model reference (developer / release / license / link / benchmarks / lineage) the roster is drawn from. Its `Benchmarks —` and `Serving —` lines, ★ marks and generated block are script-written.
- **`docs/PARETO.md`** — generated by `node scripts/roster-report.mjs pareto`; never hand-edit.
- **`docs/SYSTEM-MENU.md`** — the system menu, settings, content browsers, and persistence.
- **`docs/manual/en.md`** / **`docs/manual/zh-TW.md`** — the player guide, English (primary) and Traditional Chinese (正體中文/台灣). Keep them in step.
- **`docs/AGENT-BRIDGE.md`** — the agent bridge: HTTP API, action vocabulary, `/state` snapshot shape. Keep in sync with `public/bridge.mjs`, `src/agent/**`, and `Game.agentAct` / `agentSnapshot`.
- **`README.md`** (repo root) — developers landing on the repo. Stack, scripts, structure, links.

> If you are unsure whether a doc needs updating, it probably does. Grep for the term you changed across `*.md` and `src/i18n/`.

Docs are **forward-only**: describe the game as it is, never as a change from an earlier version.

## 1. Run / build / test

```bash
pnpm install        # once
pnpm dev            # dev server (http://127.0.0.1:5173)
pnpm typecheck      # tsc --noEmit (must pass)
pnpm lint           # eslint (must be clean)
pnpm test           # vitest: unit tests + the balance autoplay (tests/playthrough.test.ts takes a couple of minutes)
pnpm build          # tsc + vite build (must pass)
pnpm preview        # serve the built dist on :4173
pnpm e2e            # headless Playwright playtest of the built game, both languages × both modes (needs preview running)
pnpm audio:check    # offline loudness / clipping regression of the shipped mix (headless Chrome)
pnpm bridge         # the agent-bridge relay on :8799
```

The model-data pipeline (`scripts/aa-sync.mjs`, `arch-sync.mjs`, `thinking-sync.mjs`, `gen-roster.mjs`, `roster-report.mjs`) is in §3 *Add a model*. URL flags: `?agent=1` (agent mode); dev-only `?fxgallery=1` (board FX gallery), `?soundboard` (cue audition), `?perf=1` (frame-time overlay).

**Definition of done for any change:** `typecheck`, `lint`, `test`, and `build` all green, plus the doc updates from §0. Also `audio:check` when a cue or the mix changes, and `e2e` when UI changes.

### Non-negotiable invariants

- **The sim is deterministic.** `src/sim/**` must not use `Date.now()`, `Math.random()`, or wall-clock. Use the seeded `RNG` from `core/rng.ts`. Same seed + same inputs ⇒ identical results (a test asserts this). Render and audio may use wall-clock time and their own randomness, but never touch the sim's RNG.
- **The sim has no PixiJS / DOM imports**, and never imports `mode.ts`, `outcomes.ts`, `settings.ts`, or `achievements.ts`. Rendering, audio, and UI read sim state; they never own game rules.
- **Events, not polling, drive presentation.** The sim pushes a `GameEvent` (`core/types.ts`) per request lifecycle, player action, or state transition — never per tick. Every terminal request emits exactly one `outcome`; the safety layers emit `guard` / `selfHandle`, a prefix-cache hit `cache`; actions emit `build` / `upgrade` / `deploy` / `sell`; state emits `brownout` (on transitions), `wave-start`, `wave-clear`, `incident`, `research-start`, `research-done`, `posttrain-done`, `win`, `lose`. `game.ts` drains `s.events` each frame into render (`world.onEvent`), audio (the director), the shell, and achievements. Continuous display state lives on the Tower / Request display fields, declared at construction so object shapes stay stable. `OUTCOME_STYLE` is the one vocabulary an outcome is drawn, labelled, and heard in.
- **Content is data-driven.** Add/balance request archetypes, hardware tiers, the model roster, post-training recipes, infra/eval research nodes, guardrails + other towers, and incidents by editing the `src/sim/content.ts` tables — not by branching logic elsewhere. **Waves live in `campaign-data.ts`** and are expanded by `campaign.ts`, where the whole difficulty curve is tuned. `qualityBy`, `qualityByInstant`, and `thinkTokens` are never hand-edited: they are calibrated at load (`calibrate.ts`) from the generated data.
- **One forecast.** `sim/loadForecast.ts` is the one pure estimate of how a rack serves the coming wave's mixed load. The deploy picker's ★, the fit rows, the NEXT WAVE readiness, the ESTIMATE card, and the demo all read it, so the pick a player is shown is the pick the autoplay plays by. `ui/metrics.ts` mirrors the sim's serving math read-only and must agree with it (tests check parity).
- **Display mode is presentation-only.** Normal/Expert mode lives in `src/mode.ts`; `src/sim/**` must never import or branch on it. The sim always collects its telemetry (`sim/telemetry.ts`) — Expert Mode merely chooses to show more. Both modes must stay winnable by definition, because they are the same game.
- **`RealModelMeta` (`m.real`) is display-only — the sim must never read it.** A model's real-world provenance (developer / license / release / benchmarks and their provenance) lives on `ModelDef.real` purely so Expert Mode can show where a checkpoint came from; the running sim reads only the calibrated quality vectors and the architecture fields.
- **Base models are free open weights; derived models are minted, not bought.** The candidate pool is every open-weight checkpoint with an architecture record — today 135: 52 hand-authored `ROSTER` entries + 83 generated in `roster.generated.ts`. The frontier-tolerance gate (`withinFrontierTolerance`, `ROSTER_FRONTIER_TOLERANCE = 0.06`) keeps the ones within 6% of the size ↔ capability frontier on at least one axis — today 58 active, from 0.6B to Kimi K3 at ~2.8T (`docs/PARETO.md` has the live numbers). Every active checkpoint is owned from turn one. A rack deploys one when a copy of its weights (`paramsTotalB` × its release precision, or a lower researched format the rack is set to) plus framework (and any speculative draft) memory fits a power-of-two GPU group: spanning several GPUs needs Tensor Parallelism, more than eight needs Pipeline Parallelism; GPUs beyond one copy become replicas. Post-training derives NEW checkpoints into `s.derivedModels` (resolved via `resolveModel(s, id)`), capped by what its base body can hold; a run costs Data up front and GPU time the research track borrows from serving during waves. Never bill cash for deploying a checkpoint.
- **Thinking is a property of the checkpoint.** `ModelDef.thinking` (`hybrid` / `always` / `never`) comes from the released chat template (`data/model-thinking.json`, with verbatim evidence). The engine's policy is `answerMode` (`effects.ts`): a hybrid answers latency-class `IN` traffic with thinking off, judged on `qualityByInstant`, and thinks on the rest; an always-thinker thinks everywhere; embeddings never think. Hidden tokens = `thinkTokens` × the archetype's `thinkMul`: they cost decode time, KV, and latency and are never billed.
- **Directional fidelity.** Every technique ships its real-world tradeoff *directions*: numbers may be tuned for gameplay, but a real cost (power, VRAM, quality, latency, over-refusal) may be softened, never deleted — and benefits reality does not grant may not be invented. This is the slogan made law; challenge every new model / infra node / recipe / guardrail against `docs/BLUEPRINT.md` + `docs/REFERENCE-DOSSIER.md`.
- **The campaign is a 100-wave elimination gauntlet; difficulty never plateaus.** Waves 1–100 are authored (`campaign-data.ts`, real 2023→2026 history) with tier rising monotonically 1→12, so the run is *meant* to end mid-campaign for all but the apex play; clearing wave 100 (*BOSS: The Always-On Agent Era*) flips to endless mode, which resumes at the wave-100 load and climbs every surge, seeded from the run's RNG. The roster tops out at ~2.8T and a derived checkpoint is capped by its body — every run is *supposed* to end eventually. The autoplay gate is therefore DEPTH + system usage, not victory (`tests/playthrough.test.ts`): the demo reaches `GAUNTLET_FLOOR` on every gate seed and is still knocked out before wave 100, a naive build falls between waves 6 and 14, and a fleet that could clear wave 100 clears the first endless surges.

## 3. How to make common changes

Most of these are data edits in `src/sim/content.ts` (or `campaign-data.ts` for waves) against the types in `src/core/types.ts` — verify field shapes there. After **any** of them, re-run the full gate (§1); the playthrough must still pass its depth gate and exercise the systems (the bot is NOT expected to win, only to get deep by playing well).

- **Add a request archetype:** add a `RequestTypeDef` to `REQUEST_TYPES` (stable `id`; fill every required field). It is defined by workload physics, not a costume: `inputTokens` / `outputTokens` (the prefill / decode cost basis), `latClass` (`IN` 400 ms TTFT / 40 ms TPOT · `NR` 2000 / 200 · `TO` no bound; optional `ttftSloMs` / `e2elSloMs` overrides), `ttfatSloMs` for interactive traffic (time to first *answer* token — what an always-thinker misses), `thinkMul` (share of a thinking model's budget it triggers; 0 = none), `primaryAxis` + a `difficulty` vector, `prefixShare` + `cacheable`, `refusalExposure` (how borderline its benign traffic is: multiplies both model and guard over-refusal; 0 = never refused), `pricePerMtokIn` / `pricePerMtokOut`, `trustPenalty` / `slaPenalty`, and — if it carries an attack — `hazards` (hazard → severity) plus `adversarial: true` when the whole request is the attack. Pick a `color` that never reads as a disabled grey. Give it an `ERA_TOKEN_GROWTH` row and a `BASE_INTERVAL` cadence in `campaign.ts`. Add the zh-TW `req.<id>.name` / `req.<id>.desc` (English lives in `content.ts`); reference it from a wave's `mix`; update the manuals.
- **Add a hardware tier:** add a real-GPU entry to `HW_SPECS` (per-GPU `bf16TflopsPerGpu` / `fp8TflopsPerGpu` / `fp4TflopsPerGpu` (0 before Blackwell) / `hbmGbPerGpu` / `hbmTbsPerGpu` / `tdpWattsPerGpu`, `gpus`, `cooling`, `capexUsd`, `gpuHrUsdPerGpu`, `range`, and the legacy `powerDraw` / `heat`, which nothing reads — a rack's real kW comes from `tdpWatts`); the loader fills the aggregate fields and `cost = capexUsd / CREDIT_USD`. Insert its id into `HARDWARE_TIERS` for the in-place upgrade ladder. The model-parallel plan (`effects.ts`) handles any GPU count. `cooling: 'liquid'` marks a rack that cannot be air-cooled (past ~1000 W per GPU, REFERENCE-DOSSIER §5.5): it is hard-gated behind a Liquid Cooling Loop and rejects heat only into the loop's pool (`power.ts`). Only some tiers get a buildable `TOWER_DEFS` rack (`hardwareId`; today Edge and Frontier) — the rest, the multi-GPU clusters included, are reached by in-place upgrade.
- **Add a model:** a model is three kinds of fact, each with its own source, and none of them is typed into the game by hand.
  1. **Catalog first.** Add the fact-checked entry to `docs/MODEL-CATALOG.md` (developer · release · license · params · context · official link · lineage · a short description · `confidence`), refreshed by the `gptd-model-catalog` + `gptd-newest-models` research workflows.
  2. **Benchmark pin.** Find the Artificial Analysis row that measures this exact checkpoint and pin it by UUID — `{ slug, aaId }` in `data/roster-aa-map.json` under the roster id (slugs get recycled; the UUID is what fixes the row). For a **hybrid**, also pin AA's Non-reasoning row of the same checkpoint as `instant: { slug, aaId }`; without one, its instant cells come from the pair fit. (`gen-roster.mjs` writes this pin itself for a generated pool checkpoint.)
  3. **Architecture.** Add a `data/model-arch.json` entry keyed by the Hugging Face repo: `aa` (the `{ slug: uuid }` rows that measure it — gen-roster's open-weight evidence), the developer-stated `paramsTotalB` / `paramsActiveB` (listed in `manual`), and a `config` mirror if the repo is gated. Run `node scripts/arch-sync.mjs fetch <repo> && node scripts/arch-sync.mjs extract <repo>` to read the KV layer groups, release precision, window, and license off `config.json` + the safetensors metadata (`HF_TOKEN` for gated repos; `node scripts/resolve-arch.mjs guess` drafts fields when no config can be read).
  4. **Thinking evidence.** Add a `data/model-thinking.json` entry (same repo key): `mode` `always` / `hybrid` / `never`, the `toggle`, the `source` file, and a verbatim `quote` from it; run `node scripts/thinking-sync.mjs fetch <repo> && node scripts/thinking-sync.mjs verify <repo>` (a bare `verify` checks every quote and fails while any source is uncached; `--allow-uncached` relaxes that).
  5. **Regenerate.** `node scripts/arch-sync.mjs build` (needs a thinking mode for every repo), then `node scripts/aa-sync.mjs build` (after `snapshot && bridges` when refreshing the AA pull — `bridges` also refits the instant pair fit). Cells are resolved on the frozen 2026-06-21 reference scale; a cell AA no longer publishes is bridged and labelled `≈`.
  6. **Roster entry.** Either a hand `ROSTER` entry in `content.ts` — `id`, `name`, `tier`, `variant`, `spec`, `hf: '<repo>'`, a `bench` overlay for model-card cells AA lacks (AA is merged over it), an `alignment` profile, optional `instructFollow`, `real: R(developer, released, confidence, baseModelId?, relation?)`, and `desc` (canonical English), with NO architecture / params / license / context fields — or `node scripts/gen-roster.mjs` for a pool checkpoint (stable `g_` ids; it appends the pin). Then `aa-sync build` again.
  7. **Reports.** `node scripts/roster-report.mjs catalog && node scripts/roster-report.mjs pareto && node scripts/aa-sync.mjs catalog`, and `node scripts/aa-sync.mjs report` for pin problems. The gate may prune the new model (it is then dominated for real) or a model a test names — update such tests deliberately. Real product names stay in English; `model.<id>.*` keys are the localization hook if one is ever needed. Update the manuals if they name it.
- **Add an infra tech:** add an `InfraNodeDef` via `infra({…})` in `INFRA_NODES`: `category`, `i18nKey`, a flat `effects` bag that `applyInfraEffects` (`sim/research.ts`) folds into typed `s.infra`, `requires`, optional `conflicts` (mutually exclusive nodes, enforced by `researchUnlocked` — chunked ⟂ disagg, SGLang ⟂ TensorRT-LLM), `dataCost` + `compute` in authored units (the loader scales them by `RESEARCH_DATA_SCALE` / `RESEARCH_COMPUTE_SCALE`), `optimizes`, `coupling`, `sourceRef`, and `requiresBlackwell` for an FP4-only format. Each node auto-becomes a `ResearchDef` on the infra track. Read the new switch in the `effects.ts` getters off `s.infra` (never `s.upgrades`), keep `ui/metrics.ts` in parity, and give it a real cost as well as its benefit. GQA/MLA/MoE/thinking are MODEL properties, not research nodes. Add `research.<id>.name` / `research.<id>.desc` to both locales.
- **Add a post-training method:** add a `MethodRecipe` to `METHOD_RECIPES_RAW` (`relation`, `allowedTargets`, `costData` / `costCompute`, the calibratable `gainScale` / `gainCap` / `taxScale` / `forgetScale`, `reshapesDeployment`, `requiresTech` pointing at a method unlock). Add the unlock `ResearchDef` via `tech(...)` on the infra track. The Studio engine (`sim/models.ts`) applies the run to both quality vectors of a hybrid and carries thinking support through (a reasoning run makes a `never` model `always`). Add `method.<id>.*` strings to both locales.
- **Add a guardrail or other tower:** add a `TowerDef` to `TOWER_DEFS` and its id to `BUILD_ORDER` (its build-bar slot; the ten `Q`–`P` hotkeys in `ui/help.ts` are all taken, so a new slot needs a key decision). A guardrail carries a `GuardrailSpec` (`archetype` encoder / generative / moderation, `side` input / output / both, `catches`, `baseRecall`, and either a fixed `checkLatencyMs` or `runsOnRoofline: true` + `guardParamsActiveB` / `guardHardwareId` to run a real inference on its own GPU). It screens by lane coverage (`sim/guards.ts`): copies of one archetype add coverage, not recall; different archetypes stack, each adding its latency and false positives. A new `kind` must be handled in `combat.ts` / `guards.ts` / `power.ts`, the inspect panel (`ui/panels.ts`), and a texture in `render/textures.ts`. Add zh-TW `tower.<id>.*` strings.
- **Tune model-intrinsic safety:** edit a model's `AlignmentProfile` (`safety`, `refusalStyle`, `overRefusal`) in the roster — or, in-game, that is what the Studio's safety recipes (RLHF / CAI / safety SFT) modify. The alignment tax and self-handling live in `sim/safety.ts`; over-refusal is `overRefusal` × the archetype's `refusalExposure`.
- **Add / edit a wave:** edit the `CAMPAIGN_THEMES` row in `campaign-data.ts` (a `WaveTheme`: `era` / `name` / `realEvent` / `brief` / `teaches` / `mix` of `{ typeId, weight, contextMul?, hazards? }` / `volume` band / `tier` 1–12 / optional `special` / `incident` / `boss`). Waves are demand shifts and operating shocks, never model or chip launches. `buildWave` expands the row: per-request work follows the era token table (`ERA_TOKEN_GROWTH` on the convex `eraTokenRamp`), the request count follows `waveBudget`, capped at `STEP_CAP` (`BOSS_STEP_CAP` for a boss) × the previous wave. Tune the OVERALL difficulty there, not per wave; keep `tier` non-decreasing. Add zh-TW `wave.<index>.name` / `brief` / `teaches` (0-based index); English lives in the theme table. Re-run `pnpm test`; update the manuals' campaign section.
- **Add an incident:** edit `INCIDENTS` (a `mods` multiplier bag over the `ActiveModifiers`, optional `instant` one-shot, optional `concentrate` lane funnel, `good`) — applied live by `applyIncident` in `sim.ts` through the build phase and the wave. A wave forces one through its `special` (default mapping in `themedIncidentId`, `campaign.ts`) or its explicit `incident`; otherwise it joins the seeded random roll, and a boss or every tenth wave without a signature incident gets a forced hard one. Add zh-TW `inc.<id>.name` / `inc.<id>.desc`; update the manuals. There are no cash upgrades (`UPGRADE_DEFS_RAW` is empty): serving and safety improvements live in the `s.infra` research tree and the Studio.
- **Add a board effect or sound:** consume the existing `GameEvent`s — `render/world.ts` (`onEvent`, the FX dispatch) and `audio/director.ts` (events → cue ids from `audio/cues.ts`, sounds in `audio/recipes.ts`). Per-outcome colour, glyph, cue, and severity come from `OUTCOME_STYLE`; every effect honours the comfort settings (`render/anim.ts`: reduced motion, screen shake, reduce flashing, FX level; `outcomeColor` for the colorblind palette) and the FX budget. If a new fact is needed, add a field to an existing event or a new lifecycle / transition event in `core/types.ts` — never a per-tick event. Audition with `?fxgallery=1` / `?soundboard`; run `pnpm audio:check`.
- **Retune balance:** the curve knobs live in `campaign.ts` (`ERA_TOKEN_GROWTH` / `eraTokenRamp`, `waveBudget` / `VOLUME_FACTOR` / `BOSS_BUDGET_MUL` / `STEP_CAP` / `BOSS_STEP_CAP`, `tierComplexity`, `hazardMulOf` / `novelShareOf`, `CONTRACT_BASE` / `CONTRACT_PER_TIER` / `CONTRACT_BOSS_PREMIUM`), with `CLEAR_BONUS_SCALE` and the physics / economy constants in `config.ts` and the recipe table in `content.ts`. The playthrough is the guard: if the demo cannot reach the floor, or a naive build stops falling early, the curve moved — fix the curve, not the test. The demo plays from `loadForecast.ts`, so a forecast change moves both the ★ and the demo.

## 4. Internationalization (i18n)

The app and manuals are multilingual. **Default language is English; Traditional Chinese (`zh-TW`) is the second.**

- **Never hardcode a player-facing string.** All UI text goes through `t(key, params?, fallback?)` from `src/i18n`. Add the key to **both** `src/i18n/en.ts` and `src/i18n/zh-TW.ts`, in the same `// --- topic ---` section of each file, next to its siblings. `tests/i18n.test.ts` fails on a key missing from either locale, a `{placeholder}` mismatch, or a composed key (`spec.<axis>`, `hw.<id>.name`, `research.<id>.desc`, `wave.<i>.teaches`, …) that does not resolve.
- **Content** (request / tower / wave / incident names, briefs and descriptions) keeps its canonical English in `src/sim/content.ts` and `campaign-data.ts`; the display helpers fall back to it when a locale key is missing, so those tables are the source of truth for English. Add the zh-TW translations under the matching keys (`req.<id>.*`, `tower.<id>.*`, `inc.<id>.*`, `wave.<i>.name` / `brief` / `teaches`) in `src/i18n/zh-TW.ts`. Research and method names live in both locale files.
- Keep established term choices consistent with `docs/manual/zh-TW.md`: technical terms such as `SLA`, `GPU`, `KV`, `TTFT`, `TPOT`, `Goodput`, `Router`, `Cache` stay in English. zh-TW is Taiwan Traditional Chinese.
- Pixi wraps only at spaces, so `ui/cjkWrap.ts` (installed in `main.ts`) breaks Han text for word-wrapped labels; never insert spaces into zh-TW copy to make it wrap.
- Switching language at runtime must update the UI live (most text is re-read from `t()` each frame). The language toggle persists to `localStorage` (`gptd_lang`).
- **The manuals are separate files**, not generated: `docs/manual/en.md` (English) and `docs/manual/zh-TW.md`. Update both when content changes.
